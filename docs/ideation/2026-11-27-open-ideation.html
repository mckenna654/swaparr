Ideation: Where Swaparr goes next

An open brainstorm across the whole project. Six angles produced 46 raw ideas. After merging duplicates, checking each one against the code and cutting the weak ones, 7 directions remain.

Short version. Swaparr is a good remote control, but it only knows anything while a phone has it open, and it says "done" before it has checked. The cheapest big improvement is making a source switch prove it worked (idea 1). The biggest decision is whether Swaparr gets a small always-on watcher (idea 6), because that is what history, alerts and "pin for tonight" all need.

Ideas 2 and 3 are low-risk groundwork: close a security hole in the proxy, and get real data from your Dispatcharr so future changes stop relying on guesses.

Grounding Context

Codebase Context

  • What Swaparr is today. A static page (index.html, app.js, source-picker.js, style.css) served by nginx, which forwards calls to Dispatcharr and adds the API key on the server side. It runs as one Docker image on Unraid. The latest release is v1.2.1 (5 November 2026).
  • Screens. Header stats (Streams, Clients, Bandwidth), live stream cards with their viewers and a Stop button, a Channels table limited to the first 150 rows, a settings dialog, and the source picker for reordering a channel's sources.
  • How it stays current. The browser asks Dispatcharr for stream status every 5 seconds (app.js:271-286). Nothing runs on the server side, so there is no history and there are no alerts.
  • Known gaps.
    • Tests are not run automatically on GitHub.
    • The Channels table can fire 150 requests at once.
    • DISABLE_PROXY puts the API key in the browser, which breaks the project's own rule.
    • Some code is duplicated or no longer used.
    • Swaparr has never been run against a real Dispatcharr or on a phone.
  • Open request. Issue #3 asks to show resolution, frame rate and catch-up for each source, with filters.

External context

  • Dispatcharr already switches to a backup source on its own when a stream buffers, and its plugins (IPTV Checker, Stream-Mapparr) scan for dead sources on a schedule. Nothing offers a live, phone-first view with memory.
  • Tautulli (the Plex equivalent) is loved for its history, graphs and notifications, and its paid phone app is mainly for push alerts.
  • The gaps users of comparable tools ask for: a history of failovers, push alerts, a view of provider connection limits, and "use this source tonight".
  • Dispatcharr's internal API is still changing and has no documented public event feed.

1. A source switch that proves it worked

Confidence 85%Complexity: Low–Medium
Description
Today, tapping a new source shows "Source switched … now plays X" as soon as Dispatcharr accepts the request, before anyone knows whether X actually plays. Instead, the card would say "Checking…" and watch the next few 5-second updates until the new source is live and data is flowing. Then it reports one of three outcomes:
  • "Live on X".
  • "X is still buffering after 20 s. Go back to Y?", with one tap to go back.
  • "Dispatcharr moved to Z instead".
A natural extension is a single "Find a working source" button. It tries the channel's sources in order, using the same check, and stops at the first one that plays.
Basis
direct: app.js:909-919 sends the switch and immediately shows the success message, with no check. In contrast, saving a priority order already reads the result back and checks it (source-picker.js:252-267: "Dispatcharr returned a different order."). So the less urgent action is verified and the live-TV action is not. external: Juniper's "commit confirmed" and the "Keep these display settings? Reverting in 15 s" pattern both apply a risky change and undo it unless it proves good.
Rationale
Switching sources happens at the worst moment: the match is breaking up and people are waiting. A green "success" message over a still-frozen picture is the quickest way to lose trust in the tool. It needs no new server pieces, only data the page already fetches every 5 seconds. It also sets the pattern every later action (stop, pin) can follow.
Downsides
Needs a sensible definition of "playing" (state plus data flowing), which can only be tuned against a real server. Automatically switching back could argue with Dispatcharr's own failover, so start with "offer to go back" rather than going back on its own.

2. Let the proxy do only what Swaparr needs

Confidence 85%Complexity: Low
Description
Swaparr's nginx passes any request under /dispatcharr-api/ to Dispatcharr with the admin API key attached. In practice, anyone who can open Swaparr has full admin control of Dispatcharr: users, provider accounts and settings. Swaparr uses only about eight calls. Allow exactly those (each with its method), refuse everything else, and remove the DISABLE_PROXY option that writes the key into a file the browser downloads. Optionally, keep the list of allowed calls in one small file that also drives the test mock.
Basis
direct: nginx.conf.template:13-18, a single location /dispatcharr-api/ with a catch-all proxy_pass and Authorization "ApiKey …", with no path or method limits. 40-generate-config.sh:21-25 writes "apiKey" into config.json when DISABLE_PROXY=true, and run_server.py:30-38 does the same. AGENTS.md: "The Dispatcharr API key reaches the browser only through the proxy."
Rationale
Swaparr is the piece most likely to be reachable from outside the house, because it is built for phones and sometimes sits behind Nginx Proxy Manager. Today the damage if it is exposed is "all of Dispatcharr"; after this change it is "can switch sources". It is a small config change, and it makes later ideas (alerts with buttons, sharing a link with the household) safe to consider.
Downsides
Too tight a list could block a call a future feature needs, and each new feature must add its call. Anyone using DISABLE_PROXY today would have to switch, which is probably nobody, but it deserves a line in the release notes.

3. Real data from your server, checked on every change

Confidence 80%Complexity: Medium
Description
Add a "Capture sample data" button under Server settings. It makes one read-only pass over the calls Swaparr uses, replaces channel, provider and user names with stand-ins (for example "Channel 1" and "Provider A"), strips URLs and keys, and downloads one file. You tap it once and drop the file into a session. It becomes the test data, and GitHub runs the tests on every push. That last part is currently missing: the only workflow builds and publishes the image. The container's health check could also go beyond "the page loads" and confirm that the API key works and Dispatcharr answers.
Basis
direct: docs/HANDOFF.md, "Not verified": "Not run against a real Dispatcharr instance or on a phone." tests/stream-quality.test.cjs:18 uses hand-written stream data. app.js:563-573 guesses whether stream_stats is text or an object and silently ignores mismatches. .github/workflows/ contains only docker-publish.yml. Dockerfile:15-16 checks only that the home page loads. external: record-and-replay test fixtures (Ruby's VCR, Polly.JS) are the usual answer to testing against a service you cannot run in CI.
Rationale
Every feature so far, and every idea here, rests on guesses about what Dispatcharr returns. Work happens in cloud sessions that can never reach your server, and a Dispatcharr update can quietly change its internal API. One tap from you replaces those guesses with the real shapes, and automatic tests turn "the button stopped working one Saturday" into a failed check before the release goes out. It also answers open questions behind other ideas, such as whether provider connection limits are visible at all.
Downsides
Removing names reliably is the hard part. Real channel and provider names must never reach GitHub, so the stand-in step needs its own tests. The captured data will go stale as Dispatcharr changes, so it needs refreshing now and then.

4. Show what is happening now, and when Dispatcharr switched by itself

Confidence 65%Complexity: Low–Medium
Description
The bitrate on each card is an average over the stream's whole life. A stream that froze two minutes ago can still look healthy. Instead, work out the current rate from how much data arrived between two 5-second updates, and flag a stall within one or two updates. Swaparr also already notices when a channel's source changes between updates. When Swaparr didn't make that change, label it: "Dispatcharr switched from Primary-HD to Backup-SD at 9:04 pm". This all runs in the page, with no new server pieces.
Basis
direct: app.js:440 calculates (stream.total_bytes * 8) / stream.uptime / 1000, a lifetime average. app.js:613-617 detects that stream_id changed but uses it only to reload the source list, then drops it. external: Dispatcharr switches sources itself when buffering, without telling anyone. CDN health checks use "several bad readings in a row" rules (hysteresis) so a single blip doesn't raise an alarm.
Rationale
"It looks fine in Swaparr but the TV is frozen" and "why did the picture suddenly go SD?" are the two most confusing moments in an IPTV household. Both answers are already in data Swaparr receives and throws away. This also feeds idea 1's "is it playing?" check.
Downsides
The verifier flagged a real unknown: Dispatcharr may reset its data counters when it switches sources, which would make the maths jump. That needs checking against real data (idea 3). The history only covers the time the page is open; idea 6 lifts that limit.

5. Channels tab: your channels first, details on demand

Confidence 75%Complexity: Medium
Description
The Channels tab shows the first 150 channels by number and loads every row's sources at the same moment. A household watches perhaps a dozen channels. Open the tab on "Your channels" instead: the ones seen playing recently (remembered on the phone, or later by idea 6), plus any that need attention, such as having no sources or currently running on a backup. The full list stays behind search, and a channel's sources load only when you open it.
Basis
direct: app.js:843-845 const maxRender = 150;. app.js:862 starts a sources request for every row inside the loop, and app.js:894 redraws icons once per row. This contradicts app.js:299, "Fetch sequentially to prevent tripping strict reverse proxy rate limiters (429 errors)". HANDOFF lists it as still open.
Rationale
It fixes a known risk of "too many requests" errors and slowness on a real server, the kind that could make a switch fail at the wrong moment. It fixes it by changing what the screen is for, not just by slowing the requests down, so the rows on a small screen are the ones that matter.
Downsides
"Recently watched" starts empty on a new phone until it learns. Someone browsing for an unusual channel has one extra step (search).

6. An always-on watcher: history and phone alerts

Confidence 60%Complexity: High
Description
Add a small process to the Swaparr container, next to nginx. It checks Dispatcharr every 5 seconds whether or not anyone has the page open. It keeps a compact log on the Unraid appdata folder: streams starting and stopping, sources changing (and whether you or Dispatcharr did it), buffering, and viewers joining and leaving. The page gains a "What happened" timeline, for example "Fox Footy switched sources 3 times between 8:10 and 8:40 pm". One optional setting, a notification link such as ntfy or Apprise, sends a phone alert for things like "every source failed" or "Dispatcharr switched source on a channel you're watching".
Basis
direct: the only checking happens in a browser timer (app.js:271-286), so nothing is seen while the page is closed. The image is nginx plus static files (Dockerfile:1,7). The server already holds the key (nginx.conf.template:18), so a watcher adds no new secret. Closed issue #4 already moved Dispatcharr calls from the browser into the container once. external: Tautulli's best-loved features (history, graphs, notifications) all sit on an always-on watcher. Its paid phone app is mostly push alerts. Apprise and ntfy reach many notification services with one link and are common on Unraid.
Rationale
The failures that matter happen when nobody is looking at Swaparr, and today the evidence is gone by the time you open it. This one change is what history, alerts, "use this source tonight" (idea 7) and later "suggest a better source order" all depend on. It moves Swaparr from a remote control towards a "Tautulli for Dispatcharr", a gap the research found nobody fills.
Downsides
This is the big architectural step. The container goes from "just a web server" to running its own process with saved data, which means more to maintain, a volume to set up in the Unraid template, and a second set of requests to Dispatcharr. It is best decided deliberately, after ideas 2 and 3 make the base safe and grounded in real data.

7. "Use this source tonight"

Confidence 55%Complexity: Medium
Description
Today there are two separate actions. A switch affects only what is playing now and can be undone by Dispatcharr's own failover or a restart. A priority reorder is permanent and, as its own message says, doesn't change current playback. Add a middle option: "Use this source until 3 am". It switches now, moves the source to the top, remembers the original order and puts it back afterwards. A banner shows what is pinned and when it will revert.
Basis
direct: the source picker's message "Priority updated in Dispatcharr. Current playback is unchanged." (source-picker.js, just after the save at 261-267). The switch call at app.js:909-912 is separate. The safe save-with-conflict-check path (source-picker.js:252-267) can be reused for the automatic revert. external: "pin this source for tonight" appears on the research gap list. Three of the six idea angles reached it independently.
Rationale
On big-game nights a provider's main feed is often the overloaded one. People want "use the backup tonight" without permanently changing their setup or having to remember to change it back.
Downsides
A timed revert needs something running at 3 am. Without idea 6, it can only revert the next time someone opens Swaparr. It also writes to Dispatcharr automatically, so it must refuse to revert if someone changed the order in the meantime (the existing conflict check does this).

Works best after idea 6. A simpler first version reverts when the page is next opened.
